# A3 真机探针复测：采集上限、读屏节奏与 OCR

## 1 对象与口径

本轮把方案 A3 剩下的三类人工执行测量一次跑齐：

| 测量 | 命令 | 说明 |
| --- | --- | --- |
| 采集上限 | `gtest.ps1 -Target lens_gtest_glass_probe` | 4 例，只打印不判时间，要可复制的交互桌面 |
| 抓屏排除 | 同上，`LENS_PROBE_EXCLUSION=1` 加 `-Filter` | 默认跳过，会在屏上放一个品红方块约 2.5 秒 |
| 读屏节奏 | `gtest.ps1 -Target lens_gtest_integration -Filter 'GlassDuplication.*:GlassReadPace.*'` | 3 例，约 90 秒，`LENS_GLASS_DUP_TEST=1` 放开旋转裁剪 |
| OCR 基线 | `ocr-bench.ps1 -Out test/records/ocr-baseline-2026-11-10.csv` | 21 张合成语料，Tesseract 取自 `B:/tesseract`，不读桌面不联网 |

对照是 `glass-capture-capability-2026-10-19.md` 与 `ocr-baseline-2026-10-28.md`。
带日期的快照不随源码改，所以这里另起一份，不改那两份。

## 2 采集上限

四例全绿（其中 `ExcludedWindowVanishesFromDuplication` 是补跑的，默认跳过）。

| 项 | 本次 |
| --- | --- |
| `\\.\DISPLAY1` | 1920×1080 @144 Hz，identity，NVIDIA RTX 4060 Laptop（adapter 0） |
| `\\.\DISPLAY6` | 1440×2560 @144 Hz，旋转 270，同一块 4060 |
| AMD Radeon（adapter 1） | 不挂屏幕，符合 ADR 0072 |
| DISPLAY1 桌面复制 | 不可用 `0x887A0004`，该屏回退 GDI |
| DISPLAY6 桌面复制 | 打开成功，帧 2560×1440，幕布拷回 CPU 中位 5.93 ms |
| GDI 读 1/4 屏 | 18.24 / 17.52 ms（ADR 0040 记 14.2 ms） |
| GDI 读全屏 | 15.88 / 31.79 ms（ADR 0040 记 13.4 ms） |
| 抓屏排除 | 品红匹配点排除前 1749、排除后 0，affinity 读回 `0x11` |

逐输出可用性没有变：10-19 那份的结论是同一台机器上外屏可复制、内屏不可，
本次仍是 DISPLAY1 不可、DISPLAY6 可。抓屏排除的 1749 → 0 与 10-19 的
3.4 节逐点相同，同一套网格与方块，排除在桌面复制上依然成立。

GDI 的 1/4 屏读价 17.5 到 18.2 ms，比 ADR 0040 记的 14.2 ms 高约三成；
全屏那一组第二次 31.79 ms 是明显的异常值，两次读数相差一倍，按方法文档的口径
报区间不报点值。一帧 CPU 拷贝 5.93 ms 与 10-19 的整屏拷回 1.90 ms 不是同一测量点
（本次含 AcquireFrame、Map 与读转），不做退化判断。

## 3 读屏节奏与旋转裁剪

`GlassReadPace.PacedAgainstTight` 三段各 20 秒：

| 段 | 20 s 内读取次数 | desktop read 中位 ms | p95 ms |
| --- | ---: | ---: | ---: |
| 按应用节奏读 1/4 | 258 | 17.6 | 23.8 |
| 紧循环读 1/4 | 1124 | 18.2 | 22.8 |
| 按应用节奏读全分辨率 | 260 | 22.0 | 27.0 |

紧循环把次数从 258 提到 1124，单次中位却只从 17.6 到 18.2，
所以**节奏只改变频率，不改变单次代价**。

`GlassReadPace.AreaSetsThePrice` 同一节奏只换源面积，三段各 10 秒：

| 源面积 | 中位 ms | p95 ms |
| ---: | ---: | ---: |
| 整张幕布 1.16 Mpx | 18.2 | 23.1 |
| 卡片 0.56 Mpx | 11.8 | 18.3 |
| 动作条 0.11 Mpx | 8.2 | 14.7 |

中位随面积单调下降，与 10-19 报告 3.6 节的结论一致：读价随面积走，不随节奏走。

`GlassDuplication.CropFollowsTheRotatedScreen`：DISPLAY1 因复制不可用留在 GDI，
DISPLAY6 的象限对得上，复制帧与 GDI 逐点比对相同像素 100.0%，帧 500×340。
旋转屏的裁剪可用，仍是逐屏独立判定。

## 4 OCR 基线

引擎从 10-28 的 Tesseract `5.4.0.20240606` 升到本次 `5.5.0.20241111`，
`chi_sim` 与 `eng` 的 traineddata 都还在，21 个样本全部 `ok`，没有 skip。

| 项 | 英语 11 | 简体中文 6 | 中英混排 4 |
| --- | ---: | ---: | ---: |
| 平均 CER 本次 | 0.52% | 4.88% | 12.74% |
| 平均 CER 10-28 | 0.52% | 4.88% | 12.74% |
| CER p50 / p95 本次 | 0.00% / 3.25% | 3.49% / 8.33% | 12.50% / 25.00% |
| 耗时 p50 / p95 本次 | 185.6 / 295.6 ms | 287.0 / 394.3 ms | 334.5 / 407.7 ms |
| 耗时 p50 / p95 10-28 | 136.3 / 217.6 ms | 280.4 / 372.9 ms | 257.0 / 346.3 ms |

全量 21 个样本：平均 CER 4.09%，p50 / p95 为 2.44% / 13.46%，
耗时 p50 / p95 为 265.0 / 394.3 ms。

**识别结果一字未变**：三组平均、p50、p95 与 10-28 完全相同，逐样本里最差的
`code-mixed-125-dark` 仍是 25.00%，`ui-mixed-150-light` 仍是 13.46%。
引擎升了一版没动输出，语料与 tessdata 都没换。

耗时普遍上浮：英语与混排的 p50 高约三成，中文几乎不变。
这不能只归因到引擎——同一台机器、不同时段、本机负载也不同，
10-19 那份方法文档已经写过高低差四倍的情形。要判引擎是否变慢，
得两版引擎在同一时段交替跑，本轮没有做这个对照。

## 5 结论

A3 这一层没有发现回归：采集可用性、旋转裁剪、抓屏排除、读价随面积走的规律
都与 10-19 一致；OCR 的识别质量与 10-28 逐项相同；钩子线程在上一份
`qml-scenario-2026-11-10.md` 里也是 0 次停顿。变化都在数字的小数位：
GDI 读价略高、OCR 耗时略高，都还落在本机噪声范围内，且没有逐帧百分位，
不能据此判断 60 Hz 卡顿。

## 6 没覆盖到的

- 引擎升版是否让 OCR 变慢，需要在同一时段交替跑 5.4 与 5.5 才能定。
- DISPLAY1 为何复制不可用是驱动/输出归属问题，10-19 已记过，本轮没有再查。
- 安装包只带 `eng`、`chi_sim` 需人工放入本机 tessdata 这条限制没变，
  10-28 的 1 节仍然有效。
- 这些数字来自 Debug 测试二进制与本机 Tesseract，不能当作读者机器上的耗时。
