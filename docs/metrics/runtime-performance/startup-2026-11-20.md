# 启动到就绪：`Lens is up` 的五次实测与向导惰性化建议

## 1 对象与口径

对象是 release 树 `build-ninja-release/src/app/lens.exe`（RelWithDebInfo，HEAD `61a49f80`）。测量前 `ninja -n` 报 4 个过期目标，用 `scripts/build/build-release.bat` 增量重建，耗时 11 秒；五次启动都落在 00:46 链接出的这份二进制上。

口径：`Start-Process` 脱离启动，记 PID 与 `Get-Process` 的 `StartTime`（进程创建时刻，Windows 时间戳分辨率约 15.6 ms）；终点取 `logs/lens.log` 里 `main.cpp:135` 的 `Lens is up` 行时间戳（本地时间、毫秒）；差值是两者之差。每轮只起一个进程，看到该行后只停本轮启动的 PID（等待上限 60 秒，五次都在 3 秒上下命中），停完确认 `Get-Process lens` 为空。

启动用读者自己的设置（`%APPDATA%\Lens\settings.json`，其中 `ONBOARDING.done=true`、宠物 mochi 开启），没有管理员权限、没有合成鼠标或键盘、没有截图，也没有手工改动设置文件。首轮启动时应用自己写了一次设置（`known_store.cpp:623` 的 `settings saved`），后四轮没有写；这是应用既有的启动行为，不是本测量的写入。

机器是 Windows 10.0.26200，双显卡（AMD Radeon 与 NVIDIA），2026-11-21 00:47:49 至 00:48:06 连续五轮。五轮期间没有启动其它构建或测试（唯一的构建在测量前完成）；宠物 mochi 可能在这几秒里短暂出现，进程停止后随之消失，机器负载未受控。

## 3 读法

`Lens is up` 写在 `app.exec()` 之前，所以差值覆盖整条初始化路径：进程创建与加载器、`QApplication` 与 Windows 平台插件、日志、单实例、随包数据（词表 152,058 条）、设置载入与密封、`LlmClient`、`AppController` 构造、语音引擎枚举、托盘创建、QML 引擎与 `Main.qml` 全部表面窗口（含向导）的创建、共享 D3D11 设备、输入钩子、启动 duty 的发起。它不包含 `app.exec()` 之后的一切：任何表面的首帧、玻璃抓屏、宠物出现、更新与同步的网络往返，以及读者真正点托盘菜单的路径。“启动到托盘可用” 在这里只有日志代理，没有交互验证。

时间的大头不在 QML。0.2 到 2.2 秒之间是设置载入、`AppController` 构造、语音引擎枚举与托盘创建；其中 `AppController` 构造自身约 1.4 秒（从 `update check ready` 到 `AppController ready`，以首轮为例）。QML 加载加共享设备只占最后约 0.56 秒。

**向导是建了不用的**。`Main.qml:126` 无条件实例化 `OnboardingWizard`；`ONBOARDING.done` 只决定 duty 要不要发 `wizardRequested`，不发时对象照样建好、只是不显示。五轮日志都没有 `first-run wizard raised`，所以五轮都付了向导的创建成本而没用到它。不存在不改代码的 A/B：创建是无条件的，改变显示状态要么写 `ONBOARDING.done=false`，要么用 `LENS_FORCE_ONBOARDING` 重新构建，两条都越界，因此没有测第二个变体。

惰性化的收益上界就是 QML 加载窗口（中位 0.557 秒），而这一档里还包括共享 D3D11 设备的创建。捕获口径的 401 ms 只在 `QT_QML_DEBUG` 测量构建里成立，两者不是同一口径。托盘菜单正文惰性化的先例更值得参考：2026-10-03 的实验把 8 次 `MenuRow` 的 `Text` 创建移出了启动，`startup` 的 trace wall 却从 2026.2 ms 变成 2065.3 ms，最大热点移到下一个创建的第一个 `Text`；报告结论是那部分成本属于共享的首次文本初始化。向导的 401 ms 很可能同理。

冷缓存的缺席也在数字里：五轮全是暖缓存（二进制刚链接、数据文件刚读过），第一轮 3.392 秒最高，但分不清是新二进制的杀软扫描还是首轮代价。没有重启、没有第二组五轮，`StartTime` 与日志时间都来自同一系统时钟，误差在毫秒级。

## 4 建议：本轮不改为惰性创建

- 预期节省：未证明。上界是 QML 加载窗口 0.53–0.71 秒，其中含共享设备创建；捕获口径的 0.4 秒来自 `QT_QML_DEBUG` 构建，且托盘菜单的先例说明其中相当一部分会平移到下一个创建者。真实墙钟收益要先用临时 `Loader` 构建做 A/B 才知道，现有证据不支持把 “每次启动省 0.4 秒” 写进收益栏。
- 风险（若实施）：首次运行的出现时机——`wizardRequested` 在 `runStartupDuties` 里、`app.exec()` 之前发出，懒创建必须在同一个处理函数里同步建好再 `show()`，首轮启动的成本不降，只是留在原地。测试：`tst_main.qml:426–432` 现在断言启动时向导对象存在且 `visible=false`，懒创建后对象在首次请求前不存在，用例要改写。dev 面 `state` 按 objectName 找窗口（`dev_surface.cpp:605`），`onboarding` 行在首次使用前找不到窗口，`visible` 与 `painted` 会恒报 false 与 0（玻璃 sheet 仍在），`windows.total` 也会随之变少。C++ 的玻璃 sheet 表里 `onboarding` 仍是 `sheet: true`（`surface_table.h:79`），这部分启动成本不随惰性化消失。`idle-memory-2026-10-05.md` 说改成按需建要连带重做出现动画那一层，`qml-scenario-2026-11-10.md` §3 也把它记成单独立项。
- 改动位置（若要重开）：`Main.qml:123–128`，把 `OnboardingWizard { id: onboarding }` 换成在 `onWizardRequested` 里激活的 `Loader` 或 `Component`，建好后调 `show()`。
- 重开门槛：先用临时 `Loader` 在 release 树跑同一套五轮，若中位差值下降 ≥150 ms 且场景 trace 的 `Creating` 有对应下降，再动测试与文档；否则接受现状。

## 5 没覆盖到的

- 惰性化 A/B：需要改 QML，本轮禁止。
- 首次运行的向导显示：要写 `ONBOARDING.done=false` 或用 `LENS_FORCE_ONBOARDING` 重建，两种情况都会改变读者设置或构建，不测。因此向导被抬起时的出现时机与首帧没有数字。
- 冷启动：五轮全是暖缓存，没有重启或清缓存后的数字；第一轮最高，但无法归因。
- 机器负载未控，没有复测第二组五轮；单机、单会话。
- `app.exec()` 之后：表面首帧、宠物出现、托盘交互、更新与同步，全部不在差值里。
- 托盘 “可用” 只有日志代理，没有点击验证。
