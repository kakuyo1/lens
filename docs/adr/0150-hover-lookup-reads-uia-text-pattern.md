# 0150 悬浮取词读 UI Automation 的文字模式，不用 RangeFromPoint

- **状态**：accepted
- **背景**：新闻和推特里的标题常是链接，鼠标选不中；剪贴板取词要点击或拖拽，OCR 对 “停一下就翻译” 太重。
  悬浮取词要求指针停在词上约一秒后直接翻译，不点击、不改选区。
- **决定**：
  - 用 UI Automation 的 TextPattern 读指针下的词。从命中元素往上找到提供文字模式的元素（最多 50 层），
    用 `RangeFromChild` 取该元素的文字范围，再逐词比对 `GetBoundingRectangles`，找出包住指针的那个词。
  - 不用 `RangeFromPoint`。在 Chrome 上它返回的位置是错的，链接、段落和普通文字都试过，结果都不在指针下。
  - 只读。不调用 Invoke 或默认动作（链接会跳转），不碰剪贴板，跳过密码框（`IsPassword`），跳过本进程的窗口。
  - 只对 `scanWhitelist` 里的进程生效，与自动扫描的边界一致。
  - 模式切换用独立热键，默认 `Ctrl+Alt+H`，可在设置的快捷键页修改；与截图键相同的组合被拒。模式本身不写入设置，启动时回到选区取词；悬浮模式下选区不取词。
  - 读取在工作线程进行。停留判定和词的判定是纯逻辑（`core/domain/hover_lookup`），不依赖 Windows。
- **后果**：
  - 依赖目标程序向 UIA 暴露文字模式。已在 Chrome 上验证：本地页面、NPR、Twitter 的正文、用户名与链接、新闻卡片标题。
    Edge、其他浏览器和原生应用没有验证，图片里的文字读不到。
  - 词框来自 UIA，只在若干样本上核对过与字形对齐；连字符会被拆成独立的词，它们会被判定为非词而不翻译。
  - 长段落逐词扫描，实测约 2 ms 每词，上限 200 词。
  - 两个热键都只存本机、不同步，不进设置表（`core/domain/settings_table.h`），与截图键同一条规则。
  - 被排除的方案：`RangeFromPoint`（位置错）；悬停加 OCR（每次停留都要截图，太重）；点击或双击后复制（会跳转，还改选区）。
