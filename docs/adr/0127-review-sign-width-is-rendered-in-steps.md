# 0127 复习牌的宽度按 4 px 分档预渲染，不做拉伸

- **状态**：accepted（2026-10-26）。补足 ADR 0125 留下的 “牌宽随单词变化，装进应用需要一种办法” 一条，本 ADR 定其做法。
- **背景**：牌宽 = 单词宽 + 留白，单词长度由读者的词表决定，最长 14 个字母。原型逐个单词重画整块牌，应用里不能这样做。拉伸方案（左端、右端固定，中段平铺，装饰另层）用原型自己的引擎测过：默认木牌三种宽度逐像素一致；猫、狗、幽灵的右端点状与条纹的相位随宽度错开，逐像素不成立；小鱼缸的椭圆缸身、小云朵的三团云、纸杯蛋糕随宽度加宽的杯身，整体形状本身随宽度变化，找不到可平铺的周期。
- **决定**：
  - 每只随包宠物、每个 4 px 宽度档（8 至 244 px，共 60 档），由原型的同一份引擎逐像素渲染一张帧条（sprite sheet，各帧从左到右）。生成的代码在 `scripts/pet/signs/`，原型与导出共用 `designs.mjs`。
  - 装载时选第一档宽度不小于单词宽度的那一张；字在牌面上水平居中，宽度不够的部分留给留白。
  - 清单 `data/pet/<id>/sign.json` 记录各档的宽与帧格尺寸，动效的帧数、节拍与脚线也在清单里；QML 里没有拉伸、没有分层绘制。
- **后果**：
  - 牌子比单词宽 0 至 3 px，不是逐像素匹配单词宽度；字居中，留白相差不超过 1.5 px，不影响阅读。
  - 数据：七只共 420 张帧条，约 0.63 MB 的 PNG。与拉伸方案相比，文件多，但每一档都与原型逐像素相同。
  - 改画法不再是改 QML，而是改 `designs.mjs` 后重跑 `export.mjs`，并提交生成的数据。
  - 单词超过 14 个字母时（不会出现），取最后一档，宽度会被夹住。
- **被排除的方案**：
  - 九宫拉伸——三件设计无法逐像素复现，见背景；近似则改变了选定的画法。
  - 8 px 一档——文件数减半，但牌宽比字宽多 0 至 7 px，留白差异可见。
  - 运行时按单词渲染——要在 QML 或 C++ 里再写一份绘制代码，正是 ADR 0125 排除的方案。
