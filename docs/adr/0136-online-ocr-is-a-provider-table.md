# 0136 在线 OCR 由服务表登记，一家一个 Adapter

- **状态**：accepted；百度通用文字识别已实现，真实账号往返未验证。OCR.space 保留。
- **背景**：ADR 0130 把在线识别限定为明确确认的手动选区，首轮只实现了 OCR.space 一个协议，端点由读者手填。读者希望能像解释服务那样在多家 OCR 服务之间选择。但 OCR 没有 OpenAI chat completions 那样的事实标准：有单 key 的简单 REST、有云厂商的签名体系、也有视觉模型接口；把端点当作兼容性承诺会把一种服务的请求发给另一种服务。
- **决定**：在线服务由 `src/ocr/online_providers.cpp` 的编译期表登记，每行是该服务的 id、显示名、分组、默认 HTTPS 地址、令牌地址（如需要）、凭据槽、语言映射与协议枚举。设置页、`onlineConfigured()` 与工厂读同一张表；没有 Adapter 的服务不能入表，工厂对未知配置返回空而不是猜一个协议。端点留空即服务默认地址，非空是读者的显式覆盖；切换服务清空地址与全部凭据，不把旧凭据发往新服务。凭据固定为 `apiKey` 与 `secretKey` 两个槽，分别存 `OCR-API-KEY` 与 `OCR-SECRET-KEY`，与解释凭据独立。交换来的令牌只存内存，凭据、地址或服务改变即清空。在线仍只服务手动选区的明确确认：扫描、本地失败与连接检测都不构成上传授权，也没有自动重试或跨服务商切换。首批实现百度通用文字识别；腾讯云、阿里云与 Google Vision 需要各自的签名或协议 Adapter，表项与 Adapter 同时加入。
- **后果**：新增一家服务是一个 Adapter 文件、一个协议枚举值、一行表项与一个工厂分支，设置页与 duty 不改。各家几何粒度不同，OCR.space 给词框、百度通常给行框且可能整个省略坐标，结果以 `geometryLevel` 区分，缺几何时按纯文本成功，界面不得把行框当词框或把缺框当失败。百度多一次令牌交换，令牌按内存缓存；过期或被拒时丢弃，下一次显式请求重新交换。隐私确认文案必须点名所选服务，凭据条款从单钥改为双槽。真实百度账号的往返、计费与限额仍未验证；腾讯、阿里云与 Google Vision 不在本版表内。
