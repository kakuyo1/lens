# 0168 页面缓存活不过它的 COM 单元：reader 死时清缓存

- **状态**：accepted
- **背景**：自动扫描长时间运行后崩溃（2026-11-08/09，五次 0xC0000005，偏移随构建漂移但都落在 UIA 读取区域；19 小时运行的那次符号化到 `page_reader_uia` 邻域，崩溃指令是 “从悬垂对象读 vtable 后虚调用”）。机制：`PageTrack` 工作线程在自家 `ComApartment`（MTA）里创建 UIA 代理，`UiaPageReader::acquire` 把 `UiaPage` 存进进程级全局 `PageCache`；任何扫描失效（切标签、离开 Chrome、暂停、档位变化）都 `track_.reset()`，旧工作线程退出时 `CoUninitialize` 减 MTA 引用计数——若此刻无其他线程撑着 COM，单元被拆除，缓存里的代理全部悬空；新轨道同一窗口命中缓存，下一次调用即访问违例。COM 铁律是接口指针必须在其出生单元销毁前释放，这条被全局缓存绕过了。崩溃前的鼠标卡顿是同一段时间里 Chrome 侧 UIA 大查询的负载表现，不是独立故障。
- **决定**：
  - **缓存条目随 reader 而死**：`~UiaPageReader()` 调 `drop()`——仍在制造这些代理的单元内部清掉全局缓存里自己窗口的条目。缓存不再可能引用一个已拆除单元里的代理。
  - **附带修正同一窗口的陈页**：切标签不改窗口句柄，旧路径下新轨道会命中缓存的上一张标签的页面；失效即换轨、换轨即清缓存之后，这条陈页路径一并消失——每次轨道重建都从全树搜索重新找页，与 TrackCore 的 `present()` 500ms 校验共同兜底。
  - **范围**：只动生命周期，不动读取协议。`anyTextOf` 与 `warmTreeOf` 各自的单元里用后即释，原本就安全；hover 查找与树预热互不共享对象，不动。
- **后果**：
  - 失效周期（切标签、暂停往返）不再掷 “是否有别的线程撑着 MTA” 的骰子，19 小时级别的运行不再以 0xC0000005 收场。
  - 代价：每次扫描失效后的第一读多做一次全树页搜索（几百毫秒量级，工作线程承担，主线程无感）——原本缓存命中的那一次收益只在 “同一窗口内轨道未换” 的场景成立，而那个场景如今本就该重新找页。
  - 全局缓存仍保留：单轨道存活期内，多次 acquire 命中它，省掉的是同一线程内重复的全树搜索。
