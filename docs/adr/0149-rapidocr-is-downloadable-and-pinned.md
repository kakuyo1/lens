# 0149 RapidOCR 可以由 Lens 下载，钉死并校验

- **状态**：accepted（2026-10-31）。部分取代 ADR 0132 的 “Lens 不分发该程序与模型，只支持读者自行安装” 与 `docs/metrics/ocr-baseline-2026-10-28.md` §2 的同一句话；0132 的 ASCII 边界、显式检测信任与 0133 的引擎清单全部保留。
- **背景**：RapidOCR-json v0.2.0 此前要求读者自备——自己找发行包、解压到 ASCII 路径、手选两个路径再检测信任。本地语音（ADR 0135）已经给出 “下载 → 校验 → 移除” 的成套体验，取词引擎没有理由更难。
- **决定**：设置 › OCR 引擎的 RapidOCR 块提供下载。发行物是 `hiroi-sora/RapidOCR-json` v0.2.0 的唯一资产 `RapidOCR-json_v0.2.0.7z`（73,461,693 字节，SHA-256 `7ad9b283…93c40`，审计记录在案）；解压出的七个文件（exe 与两种语言各自的检测、分类、识别与字典文件）按大小与摘要钉进目录（`src/capture/rapidocr_bundle.h`），逐字节与审计一致。移动任何一枚钉子是记 ADR 的决定，不是刷新（0135 同款）。
- **机制**：下载落 `%APPDATA%\Lens\rapidocr\`，`.part` → 大小与 SHA-256 校验 → 改名；解压用 Windows 自带的 `System32\tar.exe`（bsdtar 读 7z，已在实施时实测），解压后按内部钉子校验，失败的解压保留已校验的。7z 供手动解压。下载前用 `rapidOcrPathIsAscii` 预检根目录——用户名含中文导致的非 ASCII 根禁用下载（0132 的边界原样成立）。下载完成只做一件事：把两个路径写进设置文档（照常清空信任），然后触发既有的检测流程——**信任仍只由检测写入**，下载器从不发信任。失败分类取更新下载的语义：零字节即报代理提示（GitHub 在中国大陆需要代理）。
- **后果**：安装包仍不带 RapidOCR，发布渠道仍是上游原包，Lens 只是搬运并校验；未签名、无 SBOM 的第三方风险继续写在界面上。`Remove` 删除下载目录，指向目录内的既有路径一并清空，读者的手动安装不受影响。
