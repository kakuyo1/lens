# 0074 流畅档跟随屏幕刷新率：链式取帧与一条不再多拷的读回

- **状态**：accepted（阶段 5 的延伸；依赖 ADR 0070、0072、0073；复制拒绝的屏由 ADR 0087 改用 Windows Graphics
  Capture，链式取帧与节拍对两种源相同）
- **背景**：
  - ADR 0073 的四档里，自动与流畅走同一条 16 ms 轮询（上限约 62 次/秒），区别只写在说明里。读者要的是最高档真的能跟上
    屏幕刷新率；本机外屏的模式是 1440 × 2560 @144 Hz，16 ms 的轮询在数字上也不到刷新率的一半。
  - 阶段 4 的 tally 已把一次复制帧的整段价标在 4.5~5 ms（复制 + Map + 建 QImage + 四分之一转）；60 次/秒已是四分之一到
    三分之一单核。要跟上更高的刷新率，先得把这段 CPU 价削下去，再解决取帧的节拍。
  - 节拍本身还有一层：GUI 线程上的 `QTimer` 会在空闲时被 Windows 合并，6 ms 的定时器实际按不规则的间隔到达；两次轮询
    之间产出的帧会被 `AcquireNextFrame` 合并掉。144 Hz 的显示器上，这不是一个小抖动。
- **决定**：
  - **节拍按屏幕**：自动档保持 16 ms（约 60 次/秒）的安全上限；流畅档读 `QScreen::refreshRate()`，取 `1000 / Hz` 向下取整
    并钳在 4~67 ms（144 Hz → 6 ms）。`live_` 使用 `Qt::PreciseTimer`。没有刷新率报告的屏回到 60 次/秒的保守值。
  - **链式取帧**：在流畅档、且只有一张 live 幕布、且该屏的复制可用时，工作线程用 `AcquireNextFrame(16)` 阻塞等下一帧；
    取到就发布，发布完成立即再等下一帧。GUI 定时器仍按 6 ms 走，只作为多幕布、GDI 回退和重取的交错器；链在的时候它
    的 tick 不再记 `busySkips`。链在任何一次读之后发现档位变了、幕布不再 live、出现第二张 live 幕布、或屏不可复制时结束。
    - 原因：定时器的抖动会让两帧之间只隔一次轮询的帧被合并；阻塞等帧把节拍交给桌面自己，144 Hz 的 7 ms 周期就由
      复制（实测中位 2.6~3.4 ms）决定，而不是由 Windows 的定时器合并决定。静止桌面时每次等待 16 ms 超时，反而比
      6 ms 的空转轮询省唤醒。
  - **把一帧的 CPU 路缩短**：
    - 删掉中间那张 default usage 的复制纹理：staging 纹理直接作为 `CopySubresourceRegion` 的目标，GPU 少走一遍同样的像素。
    - Map 之后不再先 `memcpy` 进 QImage、再 `transformed` 转四分之一圈：用 mapped 内存构造一个带 `RowPitch` 的 QImage 视图，
      由旋转直接写出目标图；一整张幕布因此少一次分配和一次全量拷贝。Identity 仍是一次 `copy()`。
    - 复制帧不再算指纹：`frameTouches()` 已经用脏矩形与移动矩形确认过幕布区域变了，再在 GUI 线程上缩一张 32 × 32 缩略图
      只是给已经确定要发布的帧加一次全图扫描。GDI 与首图仍走指纹门。
    - 文字色改为在整张幕布上按矩形原地采样，采样行直接读 `constScanLine`；不再为卡片区域 `copy()` 一张子图，也不再用
      `QImage::pixel()` 的逐像素格式分派。
    - `frame copy` 只计 “取到帧之后的复制 + Map + 建图 + 旋转”，不再把链式等待算进复制价。
- **后果**：
  - 真机（Release RelWithDebInfo，dev 面驱动；外屏 `\\.\DISPLAY6` 竖放，1440 × 2560，模式 144 Hz；设置面板 540 × 665
    物理像素，排除抓屏，移到外屏；流光主题）：
    - **同一段 ffplay 144 fps 后景**，复制优化前 `frame copy` 中位 5.9~6.3 ms、p95 8.3~8.6 ms，发布 687~816 帧/10 s
      （约 69~82 次/秒）；优化后中位 3.0~3.2 ms、p95 4.0~4.7 ms，发布 869~881 帧/10 s（约 87~88 次/秒），`sameSkips` 0。
      该 ffplay 自己只产出约 80 帧/秒（`fd` 增长与其媒体时钟一致），所以 87~88 是 “把它给的每一帧都发布了”，不是上限。
    - **原生 D3D11 后景**（`present-probe`，1440 × 2560 全屏，`Present(1,0)`）：一次运行里自报 133~141 帧/秒，此时链式取帧
      刚落地前后各测了一轮：
      - 链之前：`frames` 1062~1069 帧/10 s（约 106~107 次/秒），`frame copy` 中位 2.6 ms、p95 3.3~3.6 ms，`noFrame`
        约 53 次/秒。后景 137~141，幕布只拿到 106，差在 GUI 定时器的抖动与合并。
      - 链之后，同一台机器的后景自报 **89~91 帧/秒**：`frames` 853~893 帧/10 s（约 85~89 次/秒），`noFrame` 3.6~18 次/秒，
        `frame copy` 中位 2.6~3.4 ms。幕布发布的就是后景产出的那些帧，差的几个是窗口拖动/重取与统计窗口边缘。
    - **后景自己的上限不是玻璃**：后景 `ffplay`/Chrome 的 rAF/原生 swapchain 在同一时段分别只报约 80、90、89~91 帧/秒；
      在省电档（玻璃完全不 live）下原生后景仍报 89~91，Chrome rAF 也报 90。显示模式与 `EnumDisplaySettings` 一直报
      144 Hz，原生 swapchain 的最早一轮确实到过 137~141，随后整机回到约 90，强制重设同一模式也不改变。故**桌面合成器
      在这一时段的产帧率约为 90**，桌面复制只能拿到合成器实际合成的帧；这是采集源的天花板，不是本次链式取帧没跟上。
      这个 90 与 144 的差仍未收口（候选：DWM/GPU 的电源状态、VRR、其它进程的合成负载），不以 “已支持 144” 记。
  - **内存**（链式取帧开启，设置面板 live、流光、外屏）：400 轮快速改 `liquidBlur`（1~100）与 `liquidRefraction`（0~40），
    每轮两次设置写入，共 800 次，耗时约 66 s；期间约 89 次/秒发布。私有内存 535.8 → 644.5 MB 后停止变动，随后 20 s
    稳定在 640.5~640.8 MB；线程 196 → 183，句柄 4705 → 4655，没有往回长。另有一次更早的 850 s / 5393 轮（10791 次写入）
    长跑（幕布当时因窗口位于屏边而被清空，不是 live 路径）：私有内存在中段 707 MB 左右持平，停止写入后回落到 417 MB。
  - 只有一张 live 幕布时链才接管节拍；多张 live 幕布仍交给 6 ms 定时器交错，每张的实际帧率是节拍除以张数。定时器在链运行
    时仍每 6 ms 醒一次（空转），这是为了保留多幕布与 GDI 的入口；它的 tick 不再计入 `busySkips`。
  - 链的阻塞上限是 16 ms；一次拖动触发的 `followDeferred` 读若排在链的等待之后，最多晚一个等待。幕布在用的图仍覆盖窗口。
  - 仍留着的价：GUI 线程上每帧一次的纹理解包（`createTextureFromImage`）与一次 QML 合成；要把这一段也拿掉，需要把 D3D11
    纹理直接交给 Qt 场景图。Qt 6.9 的 `QRhiTexture::createFrom(NativeTexture)` 已在公开头里，但还要解决跨设备共享与场景
    图线程的生存期，未在本阶段做。
- **被排除的选项**：
  - 把自动档也提到刷新率：默认档在弱机、电池和视频后景上会凭空多烧 CPU；要最高是流畅档的显式选择（ADR 0073）。
  - 用 GUI 线程上的 `QTimer(0)` 或高频 `PreciseTimer` 追帧：空转烧 CPU，而且仍会被 Windows 合并；阻塞等帧才是桌面自己的节拍。
  - 用 `timeBeginPeriod(1)` 改系统定时器精度：影响全机功耗，且不解决 “两次轮询之间的帧已被合并” 这件事。
  - 对复制帧继续算指纹：脏矩形已经回答过 “幕布区域变没变”，指纹只能再花一次全图扫描。
