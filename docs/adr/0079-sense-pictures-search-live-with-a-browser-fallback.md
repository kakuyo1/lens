# 0079 义项图走实时搜索并兜底到浏览器

- **状态**：accepted
- **背景**：词卡只给文字，抽象词够用，具体名词（`trowel`、`crane`）读起来仍要读者自己在脑子里拼一张图。原型 `ui-prototypes/word-images.html` 给了两种画法：A 一键把查询交给默认浏览器，B 在卡内原地展开三张图。本地图片包要求先选词、审图、整理许可，再随安装包分发；图片生成对具体名词不保证事实准确，且慢而贵；内嵌浏览器与抓取搜索结果页在体积、条款与稳定性上都不合适。
- **决定**：
  - 默认体验是卡内三图（B）：入口挂在**义项**上而不是词上，只对模型判定 “一张照片能说得更清楚” 的义项出现；一次只展开一条，义项行本身就是选择器。浏览器直达（A）保留为**兜底**，不是默认。
  - 图源走实时搜索，v1 只接 Wikimedia Commons：它的图带机器可读的许可与作者、不需要 key、能按需给 480 px 缩略图。每次读者点 `Pictures` 才请求，打开卡片不取图。
  - 稳定性靠**缓存 + 兜底**：缩略图与署名落在读者的 profile（`%APPDATA%\Lens\pictures\cache\v1\`，默认 64 MB / 30 天），第二次看同一查询不再请求；缓存没有、请求失败或结果为空时，入口一侧改为 `Open image search`，用系统浏览器打开一次英文图片搜索。
  - 不做本地图片包、不做图片生成、不做内嵌浏览器、不抓取搜索结果页。
- **后果**：
  - **图不保证每次都取到，也不保证义项正确**。Commons 没有 SLA、没有 safe-search，国内可能不可达 —— 不可达时 B 落到 A。这三条是已知代价，v1 不解决；`IMAGES.md` 9 记着它们。
  - 发送面变大：单词请求多问一个建议查询词（`imageable` / `imageQuery`），取图请求另发给 Commons，只发那个查询词，原句、选区、释义、key 与安装标识都不发。两次请求分开，图取不到不影响释义。`SECURITY.md` 与 `PRODUCT.md` 已登记。
  - `imageable` / `imageQuery` 是**建议值**，因此故意不在 schema 里声明类型：一个类型写错的建议值不该毁掉一份已经到手、已经付过钱的释义。解析层把一个 true 而没有查询词的值读成 “没有图”。
  - 图片是可选第二层：文字定义先到，图后到；图片条只让卡片向下长高，卡变高后仍由 `SurfaceHost.qml` 重新贴合。不新增表面，也不进玻璃 —— 所以 `UI.md` 的表面表不变。
  - 本地缓存能反映读者查过哪些词，是私有数据：不写日志正文、不上传、不同步；卸载行为沿用 `%APPDATA%\Lens` 的规则。
  - 换图源是一条新实现而不是改 duty：接口只收一个查询词，也不替实现假设 Commons 的 JSON 形状；接需要 key 的商业图搜要另评合规、费用与区域可达性。
