# 0146 点击即在锚点升起等待卡，答案到达后原地填入

- **状态**：accepted（2026-10-31，修订 `docs/adr/0046` 的 “卡片在第一段文字到达时就出现” 一句）
- **背景**：动作条的 “翻译 / 解释” 一按下去就退场（`press` 150 ms），而气泡要等模型把第一个字段写完才建窗口。
  本机日志里一次真实取词：动作条 17.553 消失，气泡 18.434 才出现，整份答案 18.914 到达——中间 **881 ms
  屏幕上没有任何表面**，然后卡片凭空出现。这段等待是网络与首 token 的时长，应用侧无事可做，但 “按了没反应”
  与 “卡片突然跳出” 是同一条体感的两端。另一处对照：拆解卡与校验卡在请求发出前就把句子画在卡上（`breakdown:
  "pending"`），读者按它们时从不落空。
- **决定**：
  - **读者的请求进入队列的那一刻升起一张卡**，由 `ExplanationExchange::ask()` 结算，不是 `send()` 那一刻：
    请求排在扫描批次后面时，卡片仍属于点击的那一帧。事务仍只由 exchange 拥有，duty 只把它投影成 payload
    （`docs/adr/0140`）。
  - **复用气泡那一张卡、同一个窗口**，状态由载荷的一个键 `waiting` 说明，与 `breakdown` 的三态同类。不新增
    表面：一张玻璃卡要多一个 `surface_table` 行、多一条互斥与抓屏排除的规则，代价大于所得。
  - 卡上画标签行（新词 / 已会，取自已会库）、标题（读者自己的选区，仍按 “打字速度” 写出）、三行 `line2`
    呼吸条、其下一行说明。**不画倒计时行、不给判定按钮、不给母语一瞥地球**：等待不是读者的阅读时间，还没
    被解释的词也还不是该判定的词。`countsDown` 与 `verdictButtons` 由 exchange 一次结算，QML 不推导（`docs/adr/0114`）。
  - **下钻层与扫描不升卡**：一个的答案本就画在卡片下的链上（`BubbleChainPanel` 自有一行 “Explaining …”），
    一个是被动表面，自己冒出来比空白更糟。预算耗尽也不升——动作条已经说过原因，不必再拿一张空卡说一遍。
  - **等待卡不留成死卡**，三条收场：失败走既有通知（`showNotice()` 本就先收卡）；读者换了选区、答案被判
    陈旧而不画时收卡；预算迟迟不放行、请求既不在空中也不在手上时收卡。后两条走 `apply()` 尾部一次收卡，
    判据是队列的两个事实（`inFlight()` 与 `hasHeldRequest()`），不在视图里再加计时器。
- **后果**：
  - 卡片的**高度仍会随答案到达而上跳**（底边贴锚点，长高即顶边上移）。本次不动它：等待卡把 “出现” 与 “长大”
    分成了两件事，出现不再是跳的一部分；跳动本身另立阶段测量后再定方案。预先量出最终高度不可能（长度在答案里），
    把卡片在预尺寸窗口里逐帧移动已在 `docs/adr/0055` 手测读作闪烁。
  - 关掉等待卡后，答案到达仍会把它升起来——与今天 “关掉半截卡后整份到达照样画” 是同一条规则，本次不改。
  - 卡上的呼吸条是接口里第二条循环动效，与图片条骨架同一条 `Tokens.motion.pulse`、同一套 `line2`，减少动效时
    静止（`DESIGN.md` 的 Motion 一节、`UI-SPEC.md` 4.17）。
  - 信任边界不变：等待卡上没有一像素模型文字，画的是读者自己的选区，`SECURITY.md` 关于 “先画未校验的预览”
    那条承诺不因本决定扩大。
  - 被排除的方案：动作条留守到第一帧（动作条不是答案该落的位置，也不告诉读者卡片会落在哪，留守久了读作卡死）；
    新开一张等待专用表面（见上）；只把气泡入场时长拉长（治不了 881 ms 的空屏）。
