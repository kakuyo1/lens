# 0137 有 key 时先问服务自己的模型货架

- **状态**：accepted
- **背景**：ADR 0020 把模型列表换成一条共用的、不带认证的 OpenRouter 目录，按厂商前缀切给各家。代价在 0020 的 “后果” 里已经写明：那是全行业的清单，服务不提供的名字仍然选得到。DeepSeek 读者把它撞成了日常——目录里 `deepseek` 段有 `deepseek-v4.1-flash`、`deepseek-v4.1-flash-1017` 这类条目，而 DeepSeek 的端点只收 `deepseek-flash`、`deepseek-v4-pro`（以及 `deepseek-v4-flash` 这个不在货架上的别名），选中前者只会得到一句不提模型名的 400，连接检测同样报 “请求格式错误”。读者的预期是：key 能调到的模型才该出现在列表里。
- **决定**：填了 key 且服务地址是 HTTPS 时，模型列表**先问这家服务自己**：`GET {baseUrl}/models`，带 `Authorization: Bearer <API-KEY>`，回答里的 id 原样写进当前服务商的 `MODELS` 缓存（不切前缀，也不碰别家）。服务不答、答非 200、答得不合形状或一条也没有时，回落到 0020 那条共用目录，行为与之前一字不差；没填 key 的读者走的还是回落这条路。货架回答的解析与目录分开（`parseServiceModelIds`）：`:` 变体照旧丢掉，条目写了 `architecture` 就仍按 “只含 text 才留”，没写（第一方货架的常态）就照收。触发时机一字未改：启动、换服务商、改 key、改地址、展开下拉。
- **后果**：填 key 的读者每次启动多一次带认证的出站请求，发往的地址就是他本来要发解释请求的那个，key 不出现在日志里；0020 接受的 “每次启动多一次第三方请求” 只对没填 key 的读者仍然成立。服务自己的货架可能比目录短（DeepSeek 只列两个），也可能漏掉能用的别名（`deepseek-v4-flash` 不在 DeepSeek 的货架上却能用）——字段仍可手输，0017 那条 “列表不改写当前模型” 仍然成立，所以漏掉的别名不会被换掉。转售服务（OpenRouter 自己）的货架就是整份行业目录，条目自带 `architecture`，过滤条件照旧生效，列表长度与之前相当。Custom 地址若不提供 `/models`，回落到目录，与今天一样。
