# 0048 待机是随机流，睡眠由抽签决定且会自己醒

- **状态**：accepted（2026-10-16）
- **背景**：待机原先接在一条安静计时器上：距上一次事件满 180 s 就请求 `yawn`，哈欠的 `returnTo` 是 `sleep`，而 `sleep` 是 `loop` 动作，`advance()` 因此永远不会结束它。结果是读者停手约三分钟，宠物必然躺下，**并且不再自己起来**——只有事件能叫醒它。随机待机本身是有的（每 20–40 s 从 `idlePool` 挑一个），但它与睡眠无关，读者感受到的是“随机动几下，然后三分钟一到就睡死”。
- **决定**：删掉安静计时器（`quiet` 与 `kQuietBeforeYawn`），改成每次待机等待到点时先掷一次骰子：
  - 抽到（`kNapChance`，1/12）就请求 `yawn`，走数据里那条 `returnTo: sleep`；
  - 否则从动作池里挑一个播。
  睡着后抽一个 `napFor`（`kNapMin`–`kNapMax`，90–300 s），到点 `settle()` 回待机。每日预算暂停进入的同一个动作不算打盹（`held == Role::Sleep` 时不自动醒），那个睡眠由读者结束。
  待机等待放宽到 20–90 s，最近播过的两个动作不重复（池子更小时按池子大小让路，绝不把自己饿死）。
  动作池在装载时补上**没被任何角色占用的单次动作**，所以给宠物加一个动作就同时给它加了一个待机动作。
- **后果**：
  - 宠物可能一两个小时都不睡，桌面上看不到它睡觉。这是换来的：它不会在读者刚停手时躺下不动。
  - 原先那个“哈欠被随机动作吞掉”的缺陷没有被修，而是随计时器一起消失——请求只在 `currentRole == Role::Idle` 时发出，那时不存在与它同级的动作在播。随之，随机动作不再需要挤进优先级阶梯：它由 `enter()` 直接进入，因为空闲计时器本来就占着 `Idle` 这个状态。`PHASE3.md` §3.3 写的“随机待机优先级最低”因此成立且无需新增一档 `Priority`。
  - 被排除：保留必睡但把阈值改成随机区间。它仍然把“安静久了会困”做成一个阈值，读者照样能数出来；而真正刺人的是睡着之后不自醒。
  - `animations.json` 的格式没有变，宠物包的校验规则也没有变。
